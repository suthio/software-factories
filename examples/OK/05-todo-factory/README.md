# OK：TODOアプリを作って、チケットで機能を足す

「チームで今日やることを追加・完了・削除したい」といった[題材メモ](brief.md)を渡すと、AIがブラウザで使えるTODOアプリを書きます。テストに通った版が `release/app.py` に残ります。脱出ゲームの作例でAIが書くのはマップのデータでしたが、ここでは画面や保存処理を含むコードを作ります。

## 合格したコードだけを取り出す

| 工程 | 読むもの | 出力・判定 |
| --- | --- | --- |
| 入力 | 人が書いた [`brief.md`](brief.md) | 例：「チームの今日やることを、追加・完了・削除したい。再起動しても残す」 |
| 計画 | 題材と[計画役の指示](plan/spec.md) | `plan/plan.json`。実装の順番、保存、画面の案。形式が違ったら作り直す |
| 実装 | 元の題材、計画、[受け入れ仕様](build/spec.md) | 空の `build/` に `app.py`。検査で落ちたら、同じファイルをAIが修正する |
| コードの検査 | `app.py` | Ruffで構文エラーや未定義の名前などを調べる。指摘があれば実装役に渡す |
| 動作テスト | 起動したアプリ | [HTTPで操作](build/check.py)してタスクを追加・完了・削除する。再起動後の一覧も調べる |
| 取り出し | 合格した `app.py` | 内容を変えず `release/app.py` にコピーし、工程ログとハッシュを残す |

たとえば再起動後に一覧が消えたら、動作テストが失敗し、その理由を受け取ったAIが保存処理を直します。計画と実装はそれぞれ最初の試行を含めて最大3回。どちらかが通らなければ、ログと `report.json` は残りますが、`release/app.py` は作りません。

## 起動して試す

Python 3.8以上、認証済みのCodex CLI、`uvx` を用意し、リポジトリのルートで実行します。Ruffは `uvx` で固定バージョンを使います。AIが書いたコードを実行するため、普段使いの認証情報や本番への書き込み権限がない隔離環境で試してください。動作テストはHTTPでフォームと一覧のHTMLを確認します。見た目やアクセシビリティは判定しません。

```sh
python3 examples/OK/05-todo-factory/factory.py
python3 '出力先のパス/release/app.py' --port 8000 --data todos.json
```

2行目は合格時だけ実行します。ブラウザで `http://127.0.0.1:8000/` を開いて、追加・完了・削除を試せます。`--brief` で題材メモを変えれば、読書リストやイベント準備など、同じ操作を使うアプリを作れます。新しい機能を足す場合は、題材だけでなく受け入れ仕様と検査も実行前に更新します。

## チケットを置いてアプリを更新する

`improve.py` は `inbox/` のチケットを読み、前回の合格版を作業フォルダにコピーします。AIが機能を足したら、Ruffをかけ、基本動作をテストします。今回の機能だけでなく、過去のチケットで足した機能もHTTPでテストします。落ちた場合は理由をAIに渡し、最初の試行を含めて最大3回まで試します。全部通ったときだけ `current/app.py` が指す版を切り替えます。

macOS・Linuxで、初回生成に合格した `release/app.py` を登録します。

```sh
example=examples/OK/05-todo-factory
state=$(mktemp -d)
python3 "$example/improve.py" "$state" --init '出力先のパス/release/app.py'
for ticket in "$example"/tickets/*.json; do
  name=$(basename "$ticket")
  cp "$ticket" "$state/inbox/$name.tmp" && mv "$state/inbox/$name.tmp" "$state/inbox/$name"
done
python3 "$example/improve.py" "$state" --once
```

`--once` はその時点のキューをファイル名順に処理します。`--watch` に替えると、起動している間は5秒ごとに新しいチケットを確認します。書きかけのJSONを読ませないよう、例のように一時名で置いてから名前を変えてください。同じファイル名は処理し直しません。`results/` に各チケットの結果、`runs/` に候補と `build.log` が残ります。`rejected` は試行上限、`error` は入力・実行環境などのエラーです。いずれも `current` は変えず、後続のチケットへ進みます。

- **001：状態で絞り込む。** 初期版を起点に、「未完了」「完了」で一覧の中身が変わるようにします。
- **002：未完了件数を表示する。** 001が合格していれば、絞り込みを残したまま件数表示を追加します。件数が合っていても、絞り込みを壊すと不合格です。

チケットの `request` に依頼を書き、`acceptance` に対応する検査を指定します。新しい種類のチケットを試すなら、[受け入れ仕様](acceptance/)と [`build/check.py`](build/check.py) のテストを先に用意してください。依頼文だけでは合否を判定できません。

この作例では既存データの移行や本番への反映はしません。`current` を切り替えても、起動中のサーバーは再起動しません。チケットはローカルファイルなので、GitHubへの接続も不要です。

発表では、チケット1枚でアプリがどう変わったかを先に見せます。たとえば未完了の件数を表示したあと、もともとの絞り込みも動くところを見せ、`build.log` で対応するテストを紹介します。コードの設計や読みやすさも見たい場合は、Ruffとは別にレビュー役を足せます。この作例ではRuffと動作テストで合否を決めます。

## 計画あり・なしを比べる

発表では先に `release/app.py` を操作して見せ、次に `plan/plan.json` と `build.log` を開きます。同じ題材・同じ検査で「計画あり」と「計画なし」を比べるなら、次のコマンドは計画を省いて実装から始めます。合格までの試行回数と、詰まった箇所を見比べてみてください。

```sh
python3 examples/OK/factory.py examples/OK/05-todo-factory/build --brief examples/OK/05-todo-factory/brief.md
```
