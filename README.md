# ソフトウェアファクトリー ハッカソン：ルールと作例

[イベントページ（connpass）](https://software-factoriy.connpass.com/event/413858/) / [当日の進め方](docs/event-runbook.md)

TODOアプリに「完了したタスクだけ表示したい」と頼むと、AIがコードを書き、テストに落ちたら結果を受け取って直す。通った版だけを次に使う。こうした仕事を、人が毎回指示を出さなくても進むように組んだ仕組みを、この会では**ソフトウェアファクトリー**と呼びます。

AIと会話しながらコードを書くときは、人が出力を見て次の指示を出します。この会で作るのは、そのやり取りを人が引き受けなくて済む仕組みです。たとえば、落ちたテストの入力と期待値だけを渡す。発表では、ほかの人が次の開発でも試せそうな工夫を見せ合います。

## 当日のルール案：まずは1件を自動で回す

仕様やチケットを1件渡したら、AIが作ったものをテストやAIレビューにかけます。落ちたら理由をAIに渡し、決めた上限までやり直します。**実行中は、人が「ここを直して」「これで合格」と指示を出さない。** 当日作るのは、この1件を処理する仕組みです。常時稼働や自動デプロイは必要ありません。

| タイミング | OK | NG（趣旨から外れる例） |
| --- | --- | --- |
| 実行前 | 仕様や参考資料を用意する。AIへの指示、テスト、打ち切りの条件を決める | 人がほぼ作り終えたものを渡し、AIには仕上げだけ頼む |
| 実行中 | ログを見る。テストや別のAIの判定をもとに、自動でやり直す | 人が合否を決める。途中の出力を見て指示を足す。失敗したテストを外して通す |
| 実行後 | 手を加えずに発表する候補を選ぶ。別の題材にも使える指示やテストを足し、最初から試す（同じ題材でもOK） | 発表する成果物を手で直す。出力を見て「ここだけ直して」とAIに頼む |

たとえば、E2Eテストの録画を渡し、AIにナレーションと字幕を付けてもらうのはOKです。できた動画を見て「この字幕だけ直して」と頼むのはNGです。字幕が画面からはみ出すなら、幅を測るテストをファクトリーに追加して、最初から作り直せます。同じ題材で試し直しても構いません。

合格までたどり着かなくても、入力と止まったときのログがあれば発表できます。AIを何回呼ぶか、どう検査するかは自由です。AIが1つでも、スクリプトでテスト結果を渡してやり直せれば十分です。

- 仕様には、作りたいものと完成の条件を書きます。文字数や素材のサイズに一律の上限はありません。画像や過去の成果物を参考に渡すこともできます。
- 既存のアプリを土台にしてもOKです。今回の変更まで作り込んでから渡すのはNGです。
- モデルやAPIキーは各自で用意してください（BYOK）。ローカルでもクラウドでも動かせます。
- ゲーム、ライブラリ、別のファクトリーなど、題材は自由です。R18は不可です。

## 運用では、合格した版を次の仕事に使う

運用中のアプリは毎回作り直しません。たとえば、[TODOアプリの作例](examples/OK/05-todo-factory/)では、前回テストに通った版を起点にします。

1. 「完了したタスクだけ表示したい」というチケットを渡す。AIが絞り込みを足し、追加・削除・保存と絞り込みのテストが通ったら次の版に切り替える。
2. 次に「未完了の件数を表示したい」というチケットを渡す。件数が合っていても、前の絞り込みを壊したら不合格。再試行しても通らなければ、前の版を残す。

人が優先順位を決めたり、次のチケットを書いたりするのはOKです。すでに動いている版に機能を足す、本番で見つかったバグを再現して直す、といった別の仕事だからです。落ちた候補を人が見て「このボタンだけ直して」と書き足すのは、チケットを分けてもその候補の手直しです。

運用が始まれば、問い合わせや監視で見つかった問題もチケットになります。まずは検証環境で合格版を作るところまでを自動化できます。本番に出すか、問題が出たときに元の版に戻すかは、別に決めて構いません。

## 作例：まずは手元で1つ動かす

### OK：動かせる作例

初めてなら、[金額を足すCLI](examples/OK/01-auto-retry/)からどうぞ。少し違うやり方を試したければ、同じCLIでも[テストの正解を別のコードで計算する例](examples/OK/04-reference-oracle/)があります。題材に迷ったら、[水族館の脱出ゲーム](examples/OK/02-escape-room/)の舞台を図書館や宇宙船に変えるだけでも始められます。

| 作例 | 題材 | 試せること |
| --- | --- | --- |
| [テストに落ちたらAIに直させる](examples/OK/01-auto-retry/) | 金額を合計するCLI | 終了コードや出力が違ったときに、テストの結果をAIに渡す |
| [鍵を使って脱出できるか調べる](examples/OK/02-escape-room/) | 閉館後の水族館 | マップを探索し、出口に着けない場合や鍵なしで出られる場合を見つける |
| [候補を3つ作って1つ選ぶ](examples/OK/03-select-outputs/) | 同じ仕様から作る脱出ゲーム | 同じ検査に合格した候補の中から、手を加えずに1つ選ぶ |
| [別のコードでテストの正解を出す](examples/OK/04-reference-oracle/) | 請求明細を合計するCLI | 自動で作った入力を試し、最初に正解と食い違った例をAIに渡す |
| [TODOアプリをチケットで更新する](examples/OK/05-todo-factory/) | ブラウザで使えるTODOアプリ | 前回の合格版に機能を足し、RuffとHTTPのテストを両方通ったら次の版に切り替える |
| [企画メモから短編動画を作る](examples/OK/06-video-factory/) | ナレーションと字幕付きのMP4 | 字幕の表示や読み上げを検査し、問題のあった工程に戻る（`addinginc/yt` が必要） |

### NG：人が途中で指示を出す、答えを先に作る

- [途中で人が合否を決める](examples/NG/01-human-review/)：人が「このまま進めていい」と答えるまで、AIが次に進まない。
- [発表前に成果物を手直しする](examples/NG/02-edit-output/)：生成したコードを1行直す。別々の候補から好きな部分を取ってつなぐ。
- [別セッションで同じ成果物の修正を頼む](examples/NG/03-feedback-as-new-input/)：遊んでみて足りないと感じた手がかりを、同じマップに足させる。
- [できあがったものを仕様として渡す](examples/NG/04-prebaked-output/)：人がゲームの全部屋を先に作り、AIにはJSONへの変換だけ頼む。

## 発表する順番

1. **できたもの**：入力と出力を見せます。完成しなかったら、途中までできたものや止まったときのログを見せてください。
2. **作る仕組み**：ほかの人にも試してほしい工夫を一つ紹介します。テストに落ちたときのログや、AIに渡したエラーメッセージがあると、仕組みが伝わります。時間やトークンを使ったわりに効果がなかった話も歓迎です。
