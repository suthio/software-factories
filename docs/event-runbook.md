# 当日の流れと発表の申し込み

発表枠が足りないときは、**ほかの参加者が次の開発で試せそうな工夫**を優先します。完成していなくても構いません。途中で止まったログから分かったことも、ぜひ聞かせてください。

## 19:00に説明、21:00ごろから発表

| 時刻 | 進め方 |
| --- | --- |
| 19:00〜19:15 | 趣旨とルールを説明します。主催のデモでは先にできたものを見せ、そのあと仕組みを紹介します |
| 19:15〜 | 制作開始。雑談しながらでも、一人でもOKです。ローカル・クラウドは自由。途中経過や困ったことはDiscordのイベントチャンネルへ |
| 20:45ごろ | 発表したい人は、下の例にならってチャンネルに投稿してください。最初の発表順を組む目安なので、後からでも申し込めます |
| 21:00ごろ〜 | 準備ができた人から発表します。最初の数枠は主催が投稿を見て順番を決め、以降は空き枠に追加します |

19:00の説明では「[まずは1件を自動で回す](../README.md#当日のルール案まずは1件を自動で回す)」を共有します。[TODOアプリの作例](../examples/OK/05-todo-factory/)を見せるなら、まず1枚目だけ渡して絞り込みを追加します。続けて2枚目を渡したら、件数表示だけでなく絞り込みもテストするところを見せます。

## 発表したい人はDiscordに投稿

次の例のように、試したことと見せられるものを書いてください。スライドは不要です。出せるログやスクリーンショットがあれば添えてください。

```text
題材：閉館後の水族館からの脱出ゲーム。生成できたけど、鍵なしでも脱出できてしまった
試したこと：鍵を拾えない状態でもう一度マップを探索したら、抜け道が見つかった
見せるもの：鍵なしで出口に着いたときのログと検査コード
```

たとえば同じ入力で、検査を入れる前と入れた後を見比べると、効果が伝わります。そこまで試せていなくても、失敗ログが1本あれば十分です。主催は、テストの書き方や再試行のさせ方など、なるべく違う工夫が聞けるように枠を組みます。同じ手法の発表が重なったら、続けて違いを見せてもらうこともあります。

全体で発表しきれない場合は、進行役を立てられる範囲で部屋を分けるか、Discordで共有します。部屋を分けたら、そこで聞いた「次に試したいこと」を一言ずつ、同じチャンネルに残してください。

## 1人5分を基本にする

1. **成果物（1分）**：入力と、できたものを見せます。未完成なら、止まったところをそのまま見せてください。
2. **ファクトリー（3分）**：一番話したい工夫を1つ紹介します。たとえば、落ちたテストのログをAIに渡したら、次の試行で何が変わったか。ログか差分を1つ見せると伝わります。
3. **質問（1分）**：たとえば「別のアプリでも使えそう？」。話が長くなりそうなら発表後に。時間に余裕があれば、質疑込みで10分までです。

## 主催デモ：最小の脱出ゲームファクトリー

最初に渡すメモは、たとえば「閉館後の水族館が舞台。水槽と作業メモを手がかりにする。怖すぎない雰囲気で」。部屋の並びや鍵の場所はAIに任せます。JSONの形式や「脱出には最短でも4手かかる」といったルールは、舞台を変えても使うのでファクトリー側に置きます。

| 役割 | 読むもの | 次に渡すもの |
| --- | --- | --- |
| [生成エージェント](../examples/OK/02-escape-room/agents/builder.md) | 題材、共通仕様、前回落ちた条件 | `game.json`。不合格なら同じ出力を自動で修正する |
| [機械検査](../examples/OK/02-escape-room/check.py) | `game.json` | 出口に着けるか、鍵が必須か、最短4手以上か。落ちたら理由を返す |
| [進行役のスクリプト](../examples/OK/factory.py) | 検査結果 | 合格なら終了。不合格なら理由を返して再試行。最大3回で止める |
| [レビューエージェント](../examples/OK/02-escape-room/agents/reviewer.md)（任意） | 機械検査を通った場面と手がかり | 次の行き先を推測できない箇所と根拠。最小版には入れない |

このデモでAIに任せるのは、シナリオとマップを書くところだけです。テストと再試行はスクリプトで行います。ゲームを遊ぶためのプログラムは、あらかじめ用意してあります。

```sh
python3 examples/OK/factory.py examples/OK/02-escape-room
python3 examples/OK/factory.py examples/OK/02-escape-room --brief examples/OK/02-escape-room/inputs/ship.md
```

1行目は水族館、2行目は観測船です。舞台が変わっても、「鍵を取らないと脱出できない」というテストはそのまま使えます。当日モデルの応答を待たずに済むよう、事前に生成した出力と検査ログを使っても構いません。見せる出力は、生成したままのものから選びます。

## 参考にした公開事例と、今回取り入れる部分

- [StrongDM Software Factory](https://factory.strongdm.ai/)：仕様とシナリオを使い、人のレビューなしで生成と検証を回しています。この作例で生成物とテストを分けたのは、ここを参考にしたものです。
- [Anthropicのハーネス設計](https://www.anthropic.com/research/harness-design-long-running-apps)：生成役と評価役を分け、主観的な品質も具体的な基準で評価する。今回は、機械で確かめにくい「手がかりが伝わるか」に絞ってレビュー役を試せます。
- [laiso / tj-loop](https://github.com/laiso/tj-loop)：作業するエージェントと、状態を見て継続を判断する監督役を分ける。今回は進行役をスクリプトにして、検査に落ちたときだけ生成役を呼びます。
- [mitaku / Andon](https://github.com/mitaku/andon)：実装・レビュー・マージ判定を分け、人にしか決められないことだけ人に聞きます。役割を分けるところは参考にしましたが、この作例では人への差し戻しや自動マージはしません。
